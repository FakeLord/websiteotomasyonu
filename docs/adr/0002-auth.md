# ADR 0002 — Supabase Auth SMTP Limitleri, `inviteUserByEmail` ve Custom Storage Adapter

- **Durum:** Kabul edildi
- **Tarih:** 2026-09-25
- **Bağlam:** `docs/phases/PHASE-01.md` → VERIFY_CURRENT_DOCS maddesi

## Sorun

PHASE-01.md, kodlamadan önce şu üç konunun güncel resmi dokümanlarla doğrulanmasını istiyor: (1) Supabase Auth'un yerleşik SMTP'sinin saatlik e-posta limiti, (2) `auth.admin.inviteUserByEmail` davranışı, (3) supabase-js custom storage adapter API'si (oturumun Windows Credential Manager'da saklanması için).

## Araştırma Bulguları

### 1. Yerleşik SMTP limiti — **kritik, düşük**

Supabase'in yerleşik (built-in) e-posta servisi **proje başına saatte yalnızca 2 e-posta** ile sınırlıdır (kullanıcı başına değil, tüm proje için toplam). Resmi olarak "best-effort", SLA'sız ve yalnızca geliştirme/test amaçlıdır; ayrıca yalnızca proje ekibindeki adreslere gönderim yapar.

**Karar:** MVP'de 3 kişilik ekip için bile bu limit yetersizdir (davet + şifre sıfırlama denemeleri hızla 2'yi aşar). Custom SMTP (Authentication → Emails → SMTP Settings) bağlanması **zorunlu** olarak `docs/qa/phase-01.md`'ye kullanıcı talimatı olarak eklenecek; custom SMTP ile limit saatte 30'a çıkar ve Rate Limits panelinden artırılabilir. Bu adım kod değişikliği gerektirmez, yalnızca Supabase Dashboard konfigürasyonudur.

### 2. `auth.admin.inviteUserByEmail`

`{ data, redirectTo }` opsiyonel parametreleri alır: `data` → `auth.users.user_metadata`'ya yazılır; `redirectTo` **yalnızca** projenin "Allowed Redirect URLs" listesindeyse çalışır, listede değilse **hata vermeden sessizce** Site URL'e döner. `admin-invite` Edge Function'ında `redirectTo` kullanılacaksa, bu URL'in Supabase Dashboard'da izinli listeye eklenmesi gerektiği QA dokümanına not düşülecek.

### 3. supabase-js custom storage adapter

`createClient(url, key, { auth: { storage, persistSession: true } })` içindeki `storage` nesnesi üç **async** metod bekler: `getItem(key): Promise<string | null>`, `setItem(key, value): Promise<void>`, `removeItem(key): Promise<void>`. Bu, Tauri `invoke()` çağrılarının (Rust `keyring` komutları) doğrudan bu arayüze sarmalanabileceği anlamına gelir — ek bir senkron/async köprüye gerek yok.

## Karar

- `apps/desktop/src/lib/secure-storage.ts`: yukarıdaki 3 async metodu Tauri `invoke("secret_get"|"secret_set"|"secret_delete", ...)` ile uygulayan bir sınıf; `supabase-client.ts` içinde `createClient(url, anonKey, { auth: { storage: secureStorage, persistSession: true, autoRefreshToken: true } })`.
- `docs/qa/phase-01.md`'ye şu kullanıcı adımı eklenecek: "Supabase Dashboard → Authentication → Emails → SMTP Settings'den custom SMTP bağlayın (yerleşik servis saatte yalnızca 2 e-posta gönderir, ekip testleri için yetersizdir)."
- `admin-invite` Edge Function'ı `redirectTo` kullanıyorsa, bu URL'in Dashboard'daki "Allowed Redirect URLs" listesine eklenmesi gerektiği QA dokümanına yazılacak.

## Sonuçlar

Auth akışı kod olarak doğru yazılsa bile, custom SMTP bağlanmadan gerçek ekip testleri (birden fazla davet) başarısız olur; bu operasyonel bir bağımlılıktır ve Faz 1'in "acceptance criteria"sının bir parçası olarak kullanıcıya devredilir (Claude'un Supabase Dashboard'a erişimi yoktur).

### 4. `FORCE ROW LEVEL SECURITY` + `SECURITY DEFINER` etkileşimi (migration'lar için kritik)

SPEC P.1, her tabloda `ENABLE ROW LEVEL SECURITY` + `FORCE` istiyor. `FORCE`, normalde RLS'ten muaf olan **tablo sahibini** de RLS'e tabi kılar — ama **`BYPASSRLS` özniteliğine sahip roller ve superuser'lar bundan etkilenmez** (PostgreSQL dokümantasyonu). Supabase'de migration'ları çalıştıran `postgres` rolü `BYPASSRLS` özniteliğine sahiptir. Dolayısıyla `postgres` tarafından (migration içinde) oluşturulan `SECURITY DEFINER` fonksiyonlar (`bootstrap_workspace`, `accept_invite`, `log_activity` vb.) `FORCE ROW LEVEL SECURITY` olsa bile RLS'i bypass ederek yazabilir — **tasarım güvenli**, ek bir rol/yetki ayarlamaya gerek yok.

### 5. Masaüstü uygulamasında davet kabul akışı (SPEC'te belirtilmemiş bir boşluk dolduruldu)

SPEC.md → F, "Kabul: davetli şifresini belirler, ilk girişte `accept_invite()` RPC'si üyeliği oluşturur" diyor ama davetlinin Supabase'in e-posta linkinden **masaüstü uygulamasına nasıl geçtiğini** (deep link, web sayfası vb.) belirtmiyor; Faz 0/1 kapsamındaki Tauri plugin listesinde de bir deep-link eklentisi yok.

**Karar:** `workspace_invites.token_hash`, admin'in Team ekranında gördüğü ve davetliye elden/mesajla ilettiği kısa bir davet kodunun SHA-256 hash'idir (Supabase'in kendi invite e-postasından bağımsız, uygulama içi ikinci bir mekanizma). Akış: (1) admin davet gönderir → Supabase invite e-postası + uygulama içi kod üretilir; (2) davetli e-postadaki linkle (herhangi bir tarayıcıda) Supabase şifresini belirler; (3) masaüstü uygulamasında bu e-posta/şifreyle giriş yapar (henüz hiçbir workspace'e üye değildir) → "Davet bekleniyor" ekranı görünür; (4) admin'in kendisine ilettiği kodu girer → `accept_invite(code)` çağrılır. Bu, yeni bir Tauri eklentisi (deep-link) gerektirmeyen, MVP için yeterli ve SPEC'in veri modeliyle (`token_hash` alanı) birebir uyumlu bir yorumdur. İleride gerçek deep-link istenirse `tauri-plugin-deep-link` eklenerek `accept_invite` RPC'si değişmeden bu akış web tabanlı hale getirilebilir.
